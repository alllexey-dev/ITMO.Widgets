# БАРС ИТМО: API, авторизация и получение оценок

Дата исследования: **15 сентября 2026 года**.

Это исходное исследование HAR. Реализация наложения БАРС и уточнения
live-контракта (30-минутный токен без продления, тихий повторный вход через
сессию ITMO.ID) описаны в [БАРС в приложении](bars-integration.md). Ниже сохранены границы
первичного исследования; формулировки «не проверено» относятся к тому этапу.

## Краткий результат

- **Свежий access token MyITMO не подходит для прямого обращения к API БАРС:**
  `users/current_user`, оба каталога журнала и два собственных журнала вернули
  HTTP **401**. Этот же токен успешно прочитал каталог зачётки MyITMO.
- **Access token клиента `bars` из HAR работает:** текущий пользователь и
  собственный журнал вернули HTTP **200**, без cookie, Referer и браузерной сессии.
- БАРС предоставляет подробные баллы по работам, планы оценивания, серверные
  суммы и подтверждённые результаты отдельных попыток. Основной запрос:
  `GET /backend/rest/marks/{checkpointPlanId}/{type}/{identifier}/student`.
- Для приложения важнее сначала использовать уже доступную детализацию MyITMO.
  У двух предметов за соответствующий семестр совпали все 10 ID обычных работ
  БАРС с ID контролей MyITMO. Прямой БАРС потребует отдельной авторизации;
  доступ к нему не является обязательным условием показа этих работ.
- `discipline_id` MyITMO **не совпал** с `headers.plan.discipline.id` БАРС,
  а `est_id` **не совпал** с `headers.plan.id`. Подставлять их в URL нельзя.

Это описание наблюдённого API, **не официальная полная спецификация сервера**.
Покрыты все REST-операции предоставленного HAR и дополнительно каталог методов
загруженного веб-клиента. Не посещённые разделы и серверные реализации неизвестны.

## 1. Источники и достоверность

Обозначения:

- **H** — запрос/ответ из предоставленного HAR. Индексы `H[n]` ниже — zero-based
  позиции в `log.entries`, не номера запросов из браузерного UI.
- **L** — выполненная в ходе исследования сетевая проверка.
- **J** — поведение или адрес, найденные в публичном JavaScript БАРС; это не
  доказательство доступности endpoint-а, его ответа или прав текущего пользователя.
- **Рекомендация** — предлагаемое поведение будущего клиента, не факт о сервере.

HAR охватывает 10:46:16–10:46:58 MSK: 144 записи, из них 84 к `/backend/rest/`.
Во всём файле 125 ответов 200, один 302, один 304 и 17 записей со статусом 0.

Часть повторных поисков отменяется самим веб-клиентом через Axios CancelToken (J).
У части JS-ресурсов нет тела из-за браузерного кеша; недостающие публичные файлы

## 2. Адреса и транспорт

| Назначение | Адрес |
|---|---|
| SPA | `https://bars.itmo.ru` |
| Backend base URL | `https://bars.itmo.ru/backend` |
| REST base URL | `https://bars.itmo.ru/backend/rest/` |
| OIDC issuer | `https://id.itmo.ru/auth/realms/itmo` |
| OIDC client | `bars` |
| Зарегистрированный web callback | `https://bars.itmo.ru/rest/login` |

Далее пути с `/rest/` относительны к **Backend base URL**. Не путать
`/rest/login` на домене SPA и `/backend/rest/login` на Backend.

Для проверенных защищённых GET достаточно:

```http
Accept: application/json
Authorization: Bearer <BARS_ACCESS_TOKEN>
```

Списки — голые JSON-массивы; одиночные сущности — голые объекты.
Обёртки MyITMO `result`, `data`, `error_code` у успешных ответов БАРС не наблюдались.
JSON использует одновременно snake_case и camelCase: например,
`checkpoint_plan_id`, но `regularSum`. Query — также camelCase.

В HAR отправлялись браузерные cookie, но L подтвердила, что для двух проверенных
GET они не нужны. Нельзя переносить этот вывод на login, остальные методы или
бессрочное обновление сессии. Контракт CORS для произвольного сайта не проверялся;
наличие Axios `withCredentials`/`mode` не является серверной спецификацией CORS.

## 3. Авторизация

### 3.1. Наблюдённый вход БАРС

1. Браузер открывает официальный ITMO.ID:

   ```text
   GET https://id.itmo.ru/auth/realms/itmo/protocol/openid-connect/auth
       ?response_type=code
       &scope=openid
       &client_id=bars
       &redirect_uri=https%3A%2F%2Fbars.itmo.ru%2Frest%2Flogin
   ```

2. ITMO.ID отвечает 302 на web callback с `code`, `session_state`, `iss`.
   Этот конкретный HAR начинается с уже действующей SSO-сессией; ввода пароля
   в нём нет. Пароли можно вводить только на официальной странице ITMO.ID.
3. SPA отправляет `GET /rest/login?code={code}&customRedirectUri={redirectUri}`.
   `customRedirectUri` здесь равен зарегистрированному web callback.
4. Ответ H[8]: HTTP 200, пустое тело, **response header `authorization`**
   с полным значением `Bearer …`. Это не JSON `{token: ...}`.
5. Веб-клиент хранит это значение в `localStorage.token` и передаёт как request
   header `authorization`. Его response interceptor также принимает непустой
   новый `authorization` из последующих ответов (J).

В захваченном токене `iss` совпадает с ITMO.ID, `azp = bars`, `typ = Bearer`.
Наблюдённый `exp - iat` — 1800 секунд. Это срок одного образца, не SLA.
В HAR не получен отдельный refresh token БАРС и не наблюдался refresh-flow.
При ошибке авторизации веб-клиент проверяет текущего пользователя и возвращает
его к OIDC-входу (J). Продление сессии и условия выдачи нового response header
нужно исследовать отдельно.

В наблюдённом auth URL нет `state`, `nonce`, PKCE-параметров. Это описание
существующего веб-входа, **не рекомендация копировать его безопасность**.
Для нативной интеграции нужно согласовать поддерживаемый redirect/client и
безопасный Authorization Code flow с PKCE и проверкой state. Произвольная
Android callback-схема и передача уже использованного authorization code
не проверялись. SSO может убрать повторный ввод пароля, но не отменяет получение
токена нужного клиента. Поддержка token exchange неизвестна.

### 3.2. Проверка токена MyITMO

В 10:51 MSK выполнены независимые запросы без CookieJar и без follow redirects.
Локальный refresh token был отправлен **только** на официальный token endpoint:

```text
POST https://id.itmo.ru/auth/realms/itmo/protocol/openid-connect/token
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token&client_id=student-personal-cabinet&refresh_token=<LOCAL_SECRET>
```

Ответ — 200. Проверялся полученный **access token**, не refresh token и не id token.
Ротированный refresh token сохранён только в исходный игнорируемый `.refresh-token`
с правами 0600. Проверки сопоставления зачётки также использовали обычный refresh.

| Проверка | Без токена | Невалидный Bearer | Access MyITMO | Access БАРС из HAR |
|---|---:|---:|---:|---:|
| MyITMO `/api/record_book/specializations` | — | — | 200, `error_code=0` | — |
| БАРС `/rest/users/current_user/` | 401 | 401 | 401 | 200 |
| БАРС `/rest/journal/disciplines?withCheckpointPlansOnly=true` | — | — | 401 | — |
| БАРС `/rest/journal/groups-and-flows` | — | — | 401 | — |
| БАРС собственный журнал A | — | — | 401 | — |
| БАРС собственный журнал B | 401 | 401 | 401 | 200 |

«—» означает «не выполнялось в live-матрице». Оба журнала имеют успешные ответы H.
Токен БАРС на момент L ещё не истёк. Fresh MyITMO token имел тот же issuer, но
`azp = student-personal-cabinet`; полей `aud` в двух исследованных access token
не было. JWT payload декодирован только для диагностики, не использовался как
доказательство проверки подписи.

**Вывод L:** прямое использование access token MyITMO не работает в текущей
конфигурации. Общий issuer недостаточен. Серверную причину — конкретную проверку
клиента, набора claims или иную политику — без серверного кода установить нельзя.
Запросов подбора, изменения claims, обхода авторизации, чужих student ID,
token exchange или refresh с подменой client ID не было.

## 4. Пользователь, роль и учебный период

### `GET /rest/users/current_user/`

H[11, 25, 39, 70, 130], L. Возвращает объект текущего пользователя:

| Поля | Наблюдённый wire-тип / назначение |
|---|---|
| `id`, `login` | integer и string; идентичность пользователя БАРС |
| `first_name`, `middle_name`, `last_name` | string; персональные данные |
| `user_roles` | array объектов ролей; в образце «Обучающийся» |
| `selected_role` | объект выбранной роли с capability/config flags |
| `selected_year` | string `YYYY/YYYY` |
| `selected_term` | integer: 0 — весна, 1 — осень (расшифровка J) |
| `personal_config` | array `{id, name, value}`, вначале пустой |
| `can_change_user`, `restricted_to_have_read_only_access` | boolean |
| `super_user_personal_number`, audit-поля пользователя | только null в H; ненулевой тип не установлен |

Роль содержит `id`, `name`; `selected_role` дополнительно содержит `locked`,
`selected`, `allows_white_list`, `allows_multiple`, `white_list`,
`requires_main_user_user_role`. Все wire-поля и null-only значения — в приложении
со схемой. Не использовать `user_roles[].id` как ISU, не угадывать числовой ID роли.

### `GET /rest/config/`

H[10 и повторы]. Массив `{id: integer, name: string, value: string | null}`.
Наблюдены ключи `current_year`, `current_term`, `daily_message`, `edit_bars`,
`edit_regular`, `edit_journal`, `edit_exams`, `edit_personal`, `doo_user`,
`recalculated_marks_user`, `final2_marks_user`, `moodle_user`, `rpd_constructor_user`.
Значения — строки даже у логических настроек; `daily_message`/служебные поля
не следует превращать в обязательный UI. Семантика всех edit-флагов не проверена.

### `POST /rest/config/personal`

H[13, 15, 27, 29], **не воспроизводился**: изменяет сохранённые настройки.

```json
{"name": "current_year", "value": "2025/2026"}
```

Отдельный запрос выбирает сезон:

```json
{"name": "current_term", "value": "0"}
```

HTTP 200: объект `{id: integer, name: string, value: string}`.
Наблюдён переход `2026/2027, осень` → `2026/2027, весна` → `2025/2026, весна`.
**0 здесь не «весь год» и не сквозной семестр.** Сквозные семестры представлены
отдельно в `terms` плана/каталога. UI J подписывает 0 как весенний, 1 как осенний.

У каталогов журнала в H и J нет параметров `year`/`term`. Они работают в контексте
сохранённого выбора пользователя. Это делает массовую фоновую загрузку разных
периодов потенциально конфликтующей с открытым веб-БАРС. Read-only исследование
эти настройки не меняло. Возможность независимого, полностью stateless запроса
периода пока не подтверждена; не добавлять выдуманные query.

### `POST /rest/users/set_selected_role`

H[41, 99], **не воспроизводился**. Веб-клиент передал объект из `user_roles`:
`id`, `name`, `created_by`, `updated_by`, `created_at`, `updated_at`, `main_user`.
Все пять последних полей в образце null. Ответ 200 с пустым телом.
Не доказано, достаточно ли отправлять только `id`. Это выбор уже разрешённой
роли, а не способ получить дополнительные права.

## 5. Каталоги журнала и идентификаторы

### `GET /rest/journal/disciplines`

H[48–57, 72–82, 94, 101–109, 132–143]. HTTP 200: `Discipline[]`, иногда `[]`.

| Query | Доказательство | Назначение |
|---|---|---|
| `withCheckpointPlansOnly=true` | H/J | Фильтр дисциплин с планами; именно так открывается журнал |
| `name` | H/J | Поисковая строка; точный алгоритм поиска/регистр не проверен |
| `identifier`, `type` | H/J | Выбранный поток/группа; в H `type=flow` |
| `distinctByCheckpointPlans` | J | Клиентский фильтр; серверный эффект не проверен |
| `size` | J | Размер выборки; серверный лимит/default не установлен |

H содержит и запрос без query. Клиент J обычно опускает false/пустые параметры;
это не доказывает семантику явно переданного `false`. Cursor/page/total count
не наблюдались. Не обещать, что отсутствие параметров снимает все ограничения.

```json
[
  {
    "id": 9001,
    "name": "Пример дисциплины",
    "terms": [2, 4],
    "checkpoint_plan_ids": [8001]
  }
]
```

`id` — идентификатор дисциплины **БАРС**; `terms` — сквозные номера семестров,
а не сезонный `selected_term`. Один план может подходить нескольким семестрам:
в H у одного плана `terms=[2,4,6]`. Массив `checkpoint_plan_ids` — связи с планами,
не список ID работ. В рассмотренном полном каталоге 10 дисциплин; это размер
выборки одного пользователя/периода, не лимит API.

### `GET /rest/journal/groups-and-flows`

H[49 и повторы]. Query `disciplineId`, `name`; J дополнительно знает
`checkpointPlanId`. Все фильтры в клиенте необязательные.

```json
[
  {
    "type": "flow",
    "name": "Пример потока",
    "identifier": "7001",
    "checkpoint_plan_ids": [8001]
  }
]
```

`identifier` — **string**, даже когда выглядит как число. Сохранять вместе с
`type`, не считать именем группы или ISU. В H непустые элементы имеют `flow`;
остальные значения type и ответы для учебных групп здесь не подтверждены.
В нефильтрованном ответе H 18 элементов; фильтр по дисциплине возвращает меньше.

### Разрешение журнала

1. Получить дисциплины и группы/потоки в выбранном контексте.
2. Найти допустимый поток для дисциплины (`disciplineId` filter или обратный
   фильтр `type` + `identifier`).
3. Пересечь `discipline.checkpoint_plan_ids` и `flow.checkpoint_plan_ids`.
4. Получить собственный журнал для полученного `checkpointPlanId`, `type`,
   `identifier`.

J берёт первое совпадение плана. **Рекомендация:** при нуле совпадений показать
отсутствие связи; при нескольких не угадывать — проверить период, данные плана
и дать разрешить неоднозначность. Порядок массива не документирован как приоритет.

Маршрут SPA:

```text
/bars/journal/{checkpointPlanId}/{barsDisciplineId}/{type}/{identifier}
```

Это HTML-страница, а не JSON API. У собственного журнала второй ID из SPA
(`barsDisciplineId`) в URL API отсутствует. H и J подтверждают порядок параметров.

## 6. Главный запрос: собственные оценки

```http
GET /backend/rest/marks/{checkpointPlanId}/{type}/{identifier}/student
Authorization: Bearer <BARS_ACCESS_TOKEN>
```

H[79, 139], L для второго журнала. В H `type=flow`. Сегмент `/student` **не содержит
studentId**: это журнал, ограниченный текущим обучающимся. В обоих ответах
`students` содержит ровно один элемент. Не превращать это наблюдение в контракт
«всегда брать students[0]» без проверки идентичности и структуры ответа.

| Поле | Тип | Назначение |
|---|---|---|
| `students` | array `StudentJournal` | Результаты доступных студентов; здесь только свои |
| `headers.plan` | `CheckpointPlan` | Полный план, включая названия работ и границы баллов |
| `headers.deadlines` | array | В обоих H пустой; схема элементов неизвестна |
| `headers.type` | string | `flow` в H |
| `headers.identifier` | string | Совпадает с идентификатором из URL |
| `headers.name` | string | Название потока/группы |

Отдельный GET плана для первичного отображения журнала не нужен: он уже включён.

### 6.1. `StudentJournal`

- `student_id: integer`, `student_login: string`, `student_name: string` —
  персональная идентичность БАРС. Не считать все числовые student ID ISU.
- `marks: object` — баллы и подтверждения.
- `accessibility: object` — права/условия отображения. Все наблюдённые поля boolean:
  `can_edit_current_marks`, `can_edit_additional_marks`, `can_edit_course_marks`,
  `can_edit_final_marks`, `can_edit_final1_marks`, `can_edit_final2_marks`,
  `can_approve_marks`, `can_approve_retry_marks`, `can_approve_course_project`,
  `can_approve_retry_course_project`, `has_unfilled_key_checkpoints`,
  `course_project_theme_not_approved`.
- `wants_to_increase_marks: boolean` — флаг намерения повысить результат;
  веб-клиент содержит отдельную изменяющую операцию agreement, её не вызывали.

Приложению для чтения не нужны функции выставления/подтверждения оценок.
Capability flags не заменяют серверную авторизацию и не являются оценками.

### 6.2. `marks`

| Поле | Наблюдение | Семантика |
|---|---|---|
| `regular` | array `Mark`, по 10 элементов в H | Баллы обычных контрольных работ |
| `regularSum` | number | Серверная сумма текущей аттестации |
| `final` | объект `Mark` в одном ответе, **отсутствует** в другом | Балл итоговой контрольной точки, не буквенная итоговая оценка |
| `total` | number | Серверный текущий общий результат |
| `active_approvals` | array `Approval`, 1 и 2 элемента | Подтверждённые результаты попыток, не просто последнее число |

J также обращается к `marks.additional` и к данным курсового проекта.
Их ненулевые структуры в H не получены; не объявлять по догадке частью стабильного
DTO. `final1`/`final2` встречаются в названиях прав, но это не доказательство
одноимённых полей внутри `marks`.

У H `regularSum` совпал с суммой `regular[].mark`, а `total` — с
`regularSum + final.mark` (если final есть). Это только два плоских примера:
не заменять серверную сумму такой формулой для групп, бонусов и пересдач.
Не добавлять сумму `active_approvals` к `total`.

### 6.3. `Mark`: балл отдельной работы

| Поля | Тип / смысл |
|---|---|
| `id` | integer: запись оценки; не ID самой работы |
| `checkpoint_id` | integer: связь с `Checkpoint.id` |
| `checkpoint_plan_id` | integer: связь с `CheckpointPlan.id` |
| `mark` | number: полученные баллы; дробные значения реально наблюдались |
| `type` | string: у обычных работ в H `current`, у итоговой записи `final`; не путать с `Checkpoint.type` |
| `is_absent` | boolean: отметка отсутствия; нельзя кодировать только нулём |
| `is_not_bigger_than_max` | boolean: серверный флаг отношения к максимуму; сравнение согласовано в H |
| `created_at`, `updated_at` | integer: 13-значные Unix milliseconds в H |
| `created_by`, `updated_by` | integer: авторы/редакторы записи, не ID предмета |
| `created_by_name`, `updated_by_name` | string: персональные имена авторов/редакторов |

В H у присутствующих записей `mark` не null. При отсутствии записи для работы
результат должен оставаться «не выставлен», а не 0. Пока нет образца null-балла,
не утверждать его обязательность или допустимость во всех сценариях.

Соединение: для каждой работы плана найти `Mark` по `checkpoint_id`, дополнительно
проверить `checkpoint_plan_id`. Не соединять по `Mark.id`, названию или индексу
массива. Все обычные записи H разрешились таким образом.

### 6.4. `Approval`: подтверждённый результат попытки

| Поля | Тип / смысл |
|---|---|
| `id` | integer: запись подтверждения |
| `student_id`, `student_login`, `checkpoint_plan_id` | integer, string, integer: область результата |
| `attempt` | integer: номер попытки; в H есть 1 и 2, J отображает также 3 |
| `marks_sum` | number: сумма на момент подтверждения |
| `mark_string` | string: официальное отображение результата этой попытки |
| `is_active`, `is_invalid` | boolean: состояние подтверждения; оба флага сохранять |
| `is_absent` | boolean: неявка |
| `was_recalculated` | boolean: признак пересчитанного результата |
| `course` | boolean: результат курсового проекта, а не номер курса |
| `created_at`, `updated_at`, `created_by`, `updated_by` | audit, как у Mark |
| `created_by_name`, `updated_by_name` | имена сотрудников; не нужны для списка предметов |

Во втором журнале порядок попыток — **[2, 1]**. J ищет конкретный `attempt` и
разделяет `course=true/false`; он не использует первый элемент как итог предмета.
Для приложения сохранять историю, не угадывать итог по порядку массива.
Рекомендация для краткого показа: рассматривать только не-invalid активные
подтверждения нужного вида; при неоднозначности показывать попытки раздельно.
Окончательный приоритет подтверждений должен быть отдельно закреплён контрактом.

`marks.total`, `Approval.marks_sum`, `Approval.mark_string` и `Mark.mark` — разные
понятия. Буквенную/зачётную оценку не вычислять из баллов по самостоятельно
придуманной шкале. Форматировать компактные коды (`4B`, `2FX`) только на границе UI,
сохраняя исходную строку и отдельно обрабатывая неизвестные значения.

## 7. План и контрольные точки

### `GET /rest/checkpoint_plans/{checkpointPlanId}`

H[86]. Возвращает `CheckpointPlan`, та же структура, что `headers.plan`.

| Поля | Наблюдение / смысл |
|---|---|
| `id` | integer: ID плана контрольных мероприятий |
| `gid` | string: дополнительный внешний ключ; семантика не установлена |
| `year` | string `YYYY/YYYY`: учебный год |
| `terms` | integer[]: допустимые сквозные семестры |
| `discipline` | объект `{id, name, term, course_project}`; `term` только null в H |
| `point_distribution` | integer: 70 и 80 в H; совпало с суммой `max_grade` обычных работ обоих планов, не результат студента |
| `additional_points` | boolean: признак дополнительных баллов |
| `has_course_project` | boolean: признак курсового проекта |
| `regular_checkpoints` | `Checkpoint[]`: обычные работы |
| `final_checkpoint` | `Checkpoint`: итоговая контрольная точка |
| `programs`, `components` | только пустые массивы в H; тип элементов не установлен |
| `alternate_methods`, `status`, `course_project_checkpoint` | только null в H; ненулевой wire-тип не подтверждён |
| `created_by`, `updated_by`, `created_at`, `updated_at` | integer audit |

### `Checkpoint`

| Поля | Наблюдённый тип / смысл |
|---|---|
| `id` | integer: ключ для `Mark.checkpoint_id` и вложенных связей |
| `gid` | string: внешний ключ с неподтверждённой семантикой |
| `name` | string у обычных работ, null у итоговой точки |
| `type`, `type_id` | string-подпись и integer ID из справочника типов |
| `week` | integer у обычных работ, null у итоговой; номер учебной недели, не дата дедлайна |
| `group` | boolean: признак группирующей точки |
| `key` | boolean: признак ключевой точки; условия допуска определяет сервер |
| `min_grade`, `max_grade` | number: границы баллов, **не фактическая оценка** |
| `sub_checkpoints` | array: в H только пустые; J поддерживает вложенные точки |
| `parent_checkpoint_id` | только null в H; ненулевой тип требует подтверждения |
| `max_sub_checkpoints_fillable` | только null в H; смысл ограничения понятен из имени, формат не подтверждён |
| `test_id`, `test_name` | только null в H; интеграция тестов не исследована |
| `created_by`, `updated_by`, `created_at`, `updated_at` | integer audit |

Пример минимального **синтетического фрагмента**, не полный server response:

```json
{
  "checkpoint": {
    "id": 6001,
    "name": "Работа 1",
    "type": "Практическая работа",
    "min_grade": 0.0,
    "max_grade": 10.0,
    "sub_checkpoints": []
  },
  "mark": {
    "id": 5001,
    "checkpoint_id": 6001,
    "checkpoint_plan_id": 8001,
    "mark": 7.5,
    "type": "current",
    "is_absent": false
  }
}
```

Для UI это «Работа 1 — 7,5 из 10». Не показывать `min_grade` вместо полученного
балла; не суммировать группирующую точку с её детьми. Поле `group` не является
названием учебной группы. Сохранять порядок сервера и вложенность, а неизвестные
или неполные данные обрабатывать без падения и выдуманных нулей.

### `GET /rest/checkpoint_types?type={type}`

H[87–91]: `type=regular` → 32 элемента, `type=final` → 3 элемента.
J также умеет фильтр `name`; дополнительные значения type перечислены в
клиентском каталоге только там, где подтверждены кодом.

Элемент: `{id: integer, name: string, type: string, ordering: integer,
archived: boolean, created_by, updated_by, created_at, updated_at}`.
Audit-поля здесь действительно бывают как integer, так и null.

Наблюдённые финальные подписи: «Диф. зачет», «Зачет», «Экзамен».
Обычные типы включают домашние, контрольные, практические, лабораторные работы,
тесты, эссе и другие; это расширяемый справочник, не закрытый enum.
`ordering` и `archived` принадлежат серверу; количество записей не фиксировать.

## 8. Сроки

| Метод | Наблюдение |
|---|---|
| `GET /rest/deadline/{type}/{identifier}/{checkpointPlanId}` | H[83, 142], оба 200 `[]` |
| `GET /rest/deadline` | H[96], 200 `[]`: сроки текущего пользователя |
| `headers.deadlines` в журнале | Оба раза `[]` |

Порядок параметров у deadline **отличается** от marks: сначала type/identifier,
затем план. Это подтверждается связями ID в H и вызовами J.
Непустая схема deadline, её даты, зона, связи и поведение при истечении срока
не подтверждены. Не создавать фиктивный DTO и не трактовать `week` работы как
доказанную дату дедлайна. В приложении отсутствие данных о сроках не мешает оценкам.

## 9. Связь с текущей зачёткой MyITMO

Существующий путь:

```text
GET /api/record_book/specializations
  → main_plan + semesters[].semester
GET /api/record_book/{main_plan}/{semester}
  → est_id + discipline_id + have_tree
GET /api/record_book/{est_id}  (если have_tree=true)
  → id, control_name, rate, min_value, max_value, parent_id, ...
```

L дополнительно сопоставила оба журнала H с собственными предметами MyITMO
за учебный год журнала. Кандидаты выбирались по `name.trim().casefold()`, затем
проверялись ID контролей. Названия и оценки в отчёт не сохранялись.

| Проверка | Результат |
|---|---|
| Совпадение BARS discipline ID с MyITMO discipline ID | Нет для обоих предметов |
| Совпадение BARS plan ID с MyITMO `est_id` | Нет для обоих предметов |
| Совпадение обычных BARS checkpoint IDs с MyITMO control IDs в семестре 2 | 10 из 10 у каждого предмета |
| Число контролей MyITMO у этих кандидатов | 12 и 11; не только обычные работы БАРС |
| Те же названия в семестре 1 | Кандидаты есть, совпавших checkpoint IDs — 0 |

Это сильное подтверждение связи **конкретных работ конкретного периода**, но
не универсальный межсистемный контракт ID. Численное равенство всех оценок,
даты синхронизации и выбор итоговой попытки между системами отдельно не проверялись.
Отсутствие `BARS checkpoint_plan_id` в текущем MyITMO DTO не даёт права заменить
его на `est_id`. Одно название не различает осенний и весенний экземпляр предмета.

Предлагаемая стратегия:

1. Оставить MyITMO источником официальной зачётки и доступных контрольных работ.
2. Перед прямой интеграцией БАРС определить конкретный недостающий сценарий:
   история подтверждений, дополнительное состояние точки, иные реальные данные.
3. Если такой сценарий подтверждён, завести раздельные типы идентичности:
   `MyItmoRecordbookEntryId`, `BarsCheckpointPlanId`, `BarsDisciplineId`,
   `BarsGroupOrFlowRef(type, identifier)`, плюс учебный год/семестр и владелец.
4. Связь хранить явно; проверять период и пересечение ID работ, не делать
   автоматическое объединение исключительно по названию. Неоднозначное
   соответствие подтверждает пользователь.
5. Новый официальный transport/model слой размещать в MyItmoApi после отдельного
   решения о контракте библиотеки, а не во Fragment, Android-дубликате Retrofit
   или ITMO.Widgets Core. Backend проекта не получает пользовательские refresh token.
6. Загрузка истории не должна незаметно менять серверный период пользователя БАРС.
   Разрешение этого ограничения и поддерживаемый нативный login — prerequisites.

**Ничего из этого в текущем изменении не реализовано.** Приложение, MyItmoApi,
Core и Backend не обновлялись; новых минимальных версий и публикаций нет.

## 10. Ошибки, кеш и безопасное поведение клиента

- L: 401 возвращается как JSON-объект с ключами `timestamp`, `status`, `error`,
  `message`, `path`. Полные ошибки с возможными идентификаторами не логировать.
- J: journal UI отдельно обрабатывает 403 (доступ запрещён) и 423 (пользователь
  не является студентом в выбранном году/семестре). Эти статусы **не наблюдались
  в успешных H-журналах и не провоцировались в L**.
- Остальные ошибки, включая 404, 429, 5xx, должны обрабатываться стандартно;
  конкретные тела/лимиты/Retry-After сервера здесь неизвестны.
- Успешный `[]`, отсутствующий балл, отсутствующий final и HTTP-ошибка — разные
  состояния. Ошибка не должна превращаться в «0 баллов» или пустую зачётку.
- Сетевые таймауты/отмена не меняют сохранённый успешный снимок. На 401 не выполнять
  бесконечный refresh MyITMO: он не превращает токен в BARS-compatible.
- Ключ кеша: пользователь + год/семестр + план + type/identifier. На logout
  очищать токен/персональный кеш; не показывать данные предыдущего пользователя.
- Не повторять все polling-запросы веб-клиента. `USER_CHECK_INTERVAL="1"` —
  настройка SPA, не опубликованный лимит или обязательный интервал API.
- Во feature logic использовать `AcademicTimeProvider`; epoch milliseconds
  переводить через `Instant.ofEpochMilli`, отображать с явно выбранной зоной.
  Не путать технический `updated_at` с датой экзамена.
- ID хранить в отдельных строгих моделях (`Long` для integer ID, `String` для
  identifier). Дробные баллы не приводить к int. `.trim()` применять в mapper.
- Null-only поля и элементы пустых массивов требуют дополнительных наблюдений.
  До этого оставлять точные TODO, не вводить `Any?` и не объявлять ненаблюдённую
  структуру обязательной. Детальные статистики присутствия — в schema-приложении.

Минимальная будущая тестовая матрица: 401/403/423; пустой каталог; отсутствующая
оценка против 0; дробный балл; отсутствие final; несколько попыток в обратном
порядке; invalid/неявка/course; вложенные работы без двойного суммирования;
период/роль изменены извне; неоднозначный план; совпавшее имя в другом семестре;
отмена старого запроса; неизвестные поля/типы и новые значения справочников.
Тестовые данные должны быть синтетическими, не фрагментами личного HAR.

## 11. Границы исследования

Не проверены: новый вход БАРС из Android, refresh/долгоживущая сессия БАРС,
обмен MyITMO token на BARS token, новые роли, чужие журналы, пагинация/лимиты,
непустые сроки, деревья с группами, курсовые проекты, дополнительные баллы,
пустой журнал и невыставленная individual Mark с `null`, все варианты пересдач,
история редактирования, отчёты, импорт/экспорт и административные операции.

Никакие изменяющие операции из HAR не воспроизводились. Выполнены только refresh
на ITMO.ID и ограниченные GET собственных данных/публичных ресурсов. Токены и
cookie не передавались сторонним сервисам. HAR оставлен на месте и исключён
из Git через `*.har`; он содержит действовавшие секреты и персональные данные
и не должен публиковаться даже после истечения токенов.

Первичное исследование было documentation-only: Gradle и UI-тесты тогда не требовались. Проверены
соответствие каталога HAR, схемы всех успешных JSON-ответов, ссылки документации,
форматирование и отсутствие секретов/персональных значений в новых документах.
