# Зачётка v2.1: источники данных и связь со спортом

## БАРС

API БАРС описан в библиотеке MyItmoApi (`api.bars`, javadoc моделей и README).
Access token MyITMO не принимается API БАРС (HTTP 401); нужна отдельная сессия
клиента `bars`. Идентификаторы дисциплин и записей зачётки нельзя напрямую
подставлять в URL БАРС: совпадают только ID контрольных работ, но не
`discipline_id` и не `est_id`.

По запросу пользователя добавлен чип «БАРС», который накладывает баллы и работы
БАРС на список MyITMO за тот же период; сопоставление по названию, тихое
продление сессии и ограничения описаны в [БАРС в приложении](bars-integration.md).
Текст ниже описывает данные MyITMO; их логика и связь со спортом сохраняются.

## Проверка

Read-only исследование официального MyITMO выполнено 7 сентября 2026 года.
Проверены каталог программ, доступные учебные периоды, записи зачётки,
контрольные мероприятия, каталог спортивных семестров, текущий спортивный
семестр и спортивные баллы текущего и одного исторического периода.
Запрос с историческим `semester_id` успешно вернул отличающийся ответ и список
начислений; сами значения не сохранены. Это наблюдение одного аккаунта, а не полная
спецификация всех образовательных программ.

Авторизация использовала локальный `.refresh-token`. Значения токенов,
идентификаторы аккаунта, индивидуальные результаты, имена преподавателей и
полные ответы в репозитории не сохраняются. Ротированный refresh token сохранён
только в исходный игнорируемый файл с правами `0600`.

## Кто за что отвечает

| Данные | Официальный GET endpoint | Идентификатор / семантика |
|---|---|---|
| Программы и учебные периоды | `/api/record_book/specializations` | `main_plan` — идентификатор программы для следующего запроса; `semester` — сквозной номер, а не номер спортивного семестра |
| Записи зачётки | `/api/record_book/{main_plan}/{semester}` | `est_id` — конкретная запись; `discipline_id` — дисциплина учебного плана |
| Контрольные мероприятия | `/api/record_book/{est_id}` | Запрашиваем только при `have_tree = true`; сохраняем `parent_id` и порядок сервера |
| Каталог спортивных семестров | `/api/sport/semesters/list` | Собственный `id` и подпись вида «Осень YYYY/YYYY» / «Весна YYYY/YYYY» |
| Текущий спортивный семестр | `/api/sport/semesters/current` | Свой `id`, учебный год и даты; поле `semester` нельзя напрямую приравнивать сквозному номеру зачётки |
| Спортивные баллы | `/api/sport/personal/score?semester_id={id}` | `sum.attendances`, `sum.other`; отсутствие параметра означает текущий спортивный период |

Все эти endpoints уже представлены в MyItmoApi 1.6.0. Android использует именно
эту библиотеку, без второй Retrofit-схемы. ITMO.Widgets Backend и Core не являются
источниками оценок и собственных спортивных баллов; дополнительные сервисы не
нужны для просмотра зачётки.

## Обнаруженные особенности

- Каталог содержит не только прошедшие и текущий, но и будущие учебные семестры.
  Пустой результат или ещё не выставленная оценка не означают сетевую ошибку.
  Начальный выбор учитывает `AcademicTimeProvider`, включая debug-переопределение;
  явно выбранный период восстанавливается отдельно.
- `current_score` и `rate` независимы. У физкультуры наблюдались итоговый зачёт и
  одновременно `current_score = null`. Нельзя показывать это как ноль баллов или
  выводить оценку из суммы спортивных посещений.
- `rate` содержит серверную оценку, включая дробные коды вида `4/C`, текстовый
  зачёт и `null`. UI сохраняет компактные коды (`4C`, `3D`, `2FX`), а «Незачёт» и
  «Не зачёт» больше не считаются успешной сдачей. Неизвестные значения не
  засчитываются как сданный предмет.
- У контрольного мероприятия `rate` — полученный балл, `min_value` и `max_value`
  — границы. `lower_value` не является полученным баллом. Отсутствующий результат
  показывается как «—», а не как ноль. Nullable-границы из библиотечной модели
  больше не распаковываются принудительно в Kotlin `Double`.
- `parent_id` предусмотрен контрактом; исследованные примеры были плоскими.
  Android сохраняет и умеет отображать дерево, но не суммирует родителей с детьми
  и не придумывает группы по словам «homework» или «дополнительный».
- `have_tree = false` — штатное отсутствие детализации. Такой предмет по-прежнему
  открывается, но запрос несуществующих работ не выполняется.
- Объект `teacher` может присутствовать со всеми пустыми полями. Маппер обрезает
  пробелы, исключает пустые части имени и возвращает `null` вместо пустой строки.
- История спортивных начислений `attendances` может быть `null` при наличии
  объекта `sum`. Баллы при этом доступны.
- HTTP 200 не гарантирует успех: проверяется `error_code`, в том числе 401/403.
  Ошибку API нельзя превращать в пустую зачётку или успешный нулевой спорт.

## Как связана физкультура

1. Распознаются только наблюдённые названия «Физическая культура и спорт
   (базовая)» и «Физическая культура и спорт (элективная)» после нормализации.
   Это ограниченный признак вида предмета, не универсальная идентичность дисциплины.
   При новом названии приложение не угадывает связь.
2. Сквозной нечётный семестр зачётки соответствует осени, чётный — весне.
   Сопоставляется учебный год и полная сезонная подпись из спортивного каталога.
3. Принимается только единственное совпадение. Нет совпадения, неоднозначность
   или неизвестный формат подписи — отдельное состояние, без подстановки текущего
   периода. Будущий учебный семестр не получает чужие исторические баллы.
4. Общий `core/sport/SportScoreRepository` возвращает краткий результат;
   реализация принадлежит sport/data. «Мой спорт» получает через ту же реализацию
   полные начисления. Общая `SportScoreSummary` сохраняет существующую формулу
   приложения: посещения + не более 40 бонусных баллов. Это формула текущего UI,
   а не самостоятельно подтверждённое правило выставления официального зачёта.
5. Достижение 100 не меняет `rate`, статус сдачи и количество сданных предметов.
   Сумма выше 100 остаётся видимой. Спортивная строка явно подписана «Мой спорт».
6. Debug-баллы применяются одинаково в обоих экранах только к текущему спортивному
   периоду. История ими не перезаписывается. В release провайдер отключён.
7. Ошибка спорта не скрывает официальную зачётку. Повторная загрузка доступна
   через pull-to-refresh и через кнопку повторения в деталях физкультуры.

Это синхронизация чтения и вычислений, а не запись данных в университетскую
зачётку и не фоновый обмен между двумя открытыми экранами.

## Ограничения библиотеки, которые не используются в новом UI

- Wire-поле `attempt` наблюдалось как `null`, но MyItmoApi 1.6.0 хранит его как
  primitive `int`, поэтому отсутствие превращается в 0. Номер попытки здесь не
  отображается и не участвует в статусе. Для публичного nullable-accessor нужна
  отдельная совместимая правка MyItmoApi с контрактным тестом.
- В учебном периоде присутствует числовое `sem_id`, пока отсутствующее в модели
  MyItmoApi. Его связь со спортивным `id` не подтверждена. Для связи со спортом
  оно не используется; добавлять это поле в Android DTO-копию нельзя.
- `lms_link` был пустым в исследованных ответах. На основании этого нельзя
  обещать интеграцию ресурсов или открыть несуществующую ссылку.

## Граница v2.1 / v2.2

Корневой экран остаётся небольшим списком: период, краткая сводка, предметы.
Нумерация семестров сквозная в заголовке и выборе периода: 1 курс — 1/2,
2 курс — 3/4 и далее. В запросы передаётся тот же полный `semester` из API.
`semesterInCourse` остаётся только внутренним признаком осени/весны для выбора
академического периода и сопоставления со спортом.
Поиск, ручные фильтры и среднее по несовместимым источникам баллов не добавляются.
Карточка показывает круговой прогресс баллов по шкале 100, официальный код оценки
или значок зачёта и числовой результат внутри. Для обычных предметов цвет —
небольшой акцент на кольце: зелёный для сданного, цвет ошибки для несданного, primary для ещё не выставленного
итога. Цвет не заменяет код оценки. При отсутствующих баллах кольцо пустое
и без числового результата; официальный зачёт при этом сохраняется. Значения выше 100
не обрезаются в тексте. У физкультуры синее кольцо использует баллы из «Моего
спорта» за сопоставленный семестр,
в том числе пока `rate = null`. Число 120 остаётся 120, а дуга заполняется до 100%.
Оценка/значок внутри кольца по-прежнему берутся только из официального `rate`;
достижение 100 не добавляет зачёт в сводку. При ошибке или неизвестном спортивном
периоде старые академические баллы не подставляются вместо спортивного прогресса.

Сводка визуализирует долю сданных предметов. Контрольные мероприятия разделены
тихими карточками с фактическим прогрессом относительно их собственного максимума;
при неизвестном максимуме полоса скрыта. Дочерние работы имеют небольшой отступ,
результаты групп и работ не суммируются. Повтор имени преподавателя из шапки убран,
но отличающийся преподаватель и дата конкретной работы остаются видимыми.
Детали целиком прокручиваются и обновляют официальный результат, а не показывают
неизменяемый снимок навигационных аргументов.

Кольца построены на Material `CircularProgressIndicator` 1.13.0, без отдельного
canvas-рендерера; размер учитывает font scale. Перепривязка сразу устанавливает
конечный прогресс, поэтому прокрутка и refresh не проигрывают чужой результат
из переработанной карточки. Детали физкультуры используют существующий общий
двухсекторный `CircularProgressBar`:
посещения и зачтённые бонусы различимы цветом, зазор сохраняется и при сумме выше
100. Числовые посещения/бонусы стоят рядом, пояснение лимита появляется только
при превышении 40 бонусных баллов. Официальный результат вынесен в отдельную
строку внутри той же карточки. Штатно пустая детализация работ больше не создаёт
ещё одну карточку; реальные ошибки загрузки контролей не скрываются. Сам общий
спортивный рендерер и экран «Мой спорт» не менялись.

Предмет открывается с `program_id`, `semester`, `study_year`, `entry_id`; загруженная
модель сохраняет `discipline_id`. Это контекст для будущего subject hub. Связь со
schedule subject/flow ID требует resolver и подтверждения неоднозначных названий
по этапу 17 roadmap. Сейчас не добавлены фиктивные вкладки расписания, ресурсов,
отзывов, Google Sheets или функций v2.2.

## Совместимость и проверки

- MyItmoApi: 1.6.0, без изменения публичного контракта.
- ITMO.Widgets Core: существующая зависимость 1.1.9; изменений не требуется.
- Backend: нового минимального требования нет — эта функция обращается только к
  официальному MyITMO. Backend/Core/MyItmoApi не изменялись и не публиковались.
- Unit-тесты проверяют реальные Retrofit пути и query через in-memory OkHttp
  interceptor, nullable-поля, ошибки HTTP-200, общий расчёт спорта, совпадение
  периодов, неоднозначность, debug-историю, смену периода, отмену устаревших запросов,
  сохранение контента при ошибке refresh и обновление деталей. Дополнительно
  проверяются дробные баллы, неизвестный/нулевой максимум, отсутствие результата
  в отличие от нуля, нечисловые значения и результаты выше 100.
- Изолированный debug-host запускает настоящие Fragments с вымышленными
  in-memory данными. Токены, сессия, сеть и Backend в UI-тестах не используются.
